# Codebase Map & Main Logic Flows

## Application startup and session

1. `src/main.tsx` mounts `App`.
2. `src/App.tsx` restores the Supabase session using `src/data/auth.ts` and loads shared data through `initializeSharedStore()` in `src/data/store.ts`. `src/data/tabSession.ts` keeps the per-tab Supabase storage key stable on a same-origin hard reload while isolating a genuinely duplicated tab.
3. If there is no signed-in user, `PublicHospitalHome` renders the public services and departments page. The public navbar has no generic Sign In or staff-login button; the appointment CTA opens the patient account/login modal.
4. Authenticated users are routed to their role dashboard. Each dashboard is loaded with `React.lazy` and `Suspense` so the browser loads the active role's code on demand.
5. `ihms:data-error`, `ihms:data-success`, and `ihms:data-success-message` are shared status events handled by `App.tsx`.

## Patient registration and login

- UI/form: `src/components/LoginModal.tsx`; every close and every new open resets the login, reset-password, and registration inputs.
- In local demo mode, `matchesDemoLoginIdentifier()` accepts seeded 10-digit fixture phones with or without `+91`. This leniency is demo-only; Supabase uses strict `normalizeIndianLoginPhone()` and the server route.
- Shared field rules: `src/utils/validation.ts` and `src/components/IndianPhoneInput.tsx`.
- Patient sign-up uses Supabase Auth and submits validated profile metadata (`name`, `phone`, `age`, `gender`, optional `bloodGroup`). Supabase email confirmation must be configured by the deployment.
- Profile creation: `public.create_patient_profile()` in `supabase/schema.sql`, triggered on new auth user creation.
- Email login calls Supabase Auth directly. Mobile-number login calls `api/auth-login.ts`, which rate-limits attempts, resolves exactly one matching profile server-side, verifies the password through Supabase Auth using the profile email, and returns only the session tokens to the same-origin frontend. It never exposes the email associated with a phone number.
- Profile hydration: `getSignedInProfile()` in `src/data/auth.ts` combines the `profiles` row and auth metadata.
- Patient blood group is editable from the patient dashboard. Production saves it through `public.update_my_patient_blood_group(text)`; this avoids granting users general `UPDATE` privileges on `profiles`.

## Reception walk-in and quick appointment booking

- UI and orchestration: `src/components/receptionist/ReceptionistDashboard.tsx`.
- Walk-in collects patient name, Indian phone, optional validated Gmail (required when inviting a portal account), optional age/gender/blood group, reason and doctor assignment.
- Portal invitations are sent via `src/data/staffAccounts.ts` to `/api/staff`; that endpoint authenticates the session and uses a service-role client server-side to create Auth/profile records.
- Appointments are staged through `store.addAppointment()` and persisted with `store.flushPendingWrites()`.
- The walk-in path is an immediate queue entry; online/quick bookings use a selected doctor's shift slot.

## Patient appointment booking and follow-up

- UI: `src/components/patient/PatientDashboard.tsx`.
- Candidate appointment times are generated by `getShiftAppointmentSlots(doctor.shift)` in `src/utils/staffShifts.ts`.
- When Supabase is configured, availability is retrieved through `get_booked_slots` and refreshed while the booking tab is active. Local mode compares against locally stored appointments.
- Database trigger `public.prepare_ihms_record_insert()` revalidates the doctor, appointment type/date, 15-minute time format, and that the time belongs to the doctor's assigned shift. Client controls are not treated as a security boundary.
- Appointment confirmation messages are delivered by `src/data/appointmentEmails.ts` -> `api/appointment-confirmation.ts`. The endpoint verifies ownership and uses the database claim function to prevent duplicate sends.

## Staff and shift scheduling

- Staff add forms: `src/components/admin/AdminDashboard.tsx` and `src/components/manager/ManagerDashboard.tsx`.
- Staff API client: `src/data/staffAccounts.ts`; server endpoint: `api/staff.ts`.
- Each non-patient profile uses `details.shift = 'general'`. The schema migration maps existing morning/evening/night/unassigned values to the single General Shift; patient profiles do not need a workforce shift.
- General Shift is 09:00–22:00 Asia/Kolkata with a fixed 13:00–14:00 lunch break. New attendance records auto-check out at 22:00 and record working time net of lunch.
- Appointment starts are every 15 minutes at 09:00–12:45 and 14:00–21:45. Patient and receptionist booking use `getShiftAppointmentSlots()`; API/database validation independently rejects lunch-period and out-of-hours starts.
- Staff creation assigns General Shift automatically; the UI no longer offers shift selection. `api/staff.ts` retains a protected compatibility action that only accepts `general`; it rejects future doctor appointments conflicting with the lunch window before changes.

## Persistence and synchronization

- Production records are stored in `public.ihms_records` (with appointment `owner_id` and `doctor_id`) and prescriptions in `public.ihms_prescriptions`.
- RLS and trigger functions in `supabase/schema.sql` constrain read/write behavior by role and ownership.
- `src/data/store.ts` maintains an in-browser cache and queued write operations, plus Realtime subscriptions on `ihms_records`, `ihms_prescriptions`, and `profiles`. Each role dashboard subscribes to the shared store and updates without a manual page refresh. The app reconciles again when the tab becomes visible or connectivity returns; if Realtime reports an error, it refreshes every 30 seconds while visible. `App.tsx` also refreshes the cached current-user profile so profile changes appear in the app shell.
- Local mock records in `src/data/mockData.ts` are for development/demo mode, not a production database.

## Error handling

- Form-level errors are shown beside the related form (login/registration/password modal).
- Cross-dashboard operational errors use `window.dispatchEvent(new CustomEvent('ihms:data-error', { detail: 'Safe message' }))`; `App.tsx` renders an accessible alert.
- Non-blocking success feedback uses `ihms:data-success-message`.
- Always preserve diagnostic `console.error` entries for debugging, but translate network/database failures into helpful user-facing messages.

## URL routing and role authorization

- Canonical feature paths and authorization mapping: `src/utils/workspaceRoutes.ts`.
- Tab/filter state synchronizes with browser URL/Back/Forward: `src/hooks/useWorkspaceTab.ts`.
- The route guard prevents unauthorized dashboard rendering and validates post-login redirects: `src/App.tsx`.
- Direct-route SPA rewrites: `vercel.json` (`/login` and `/portal/:path*` only; API routes are not rewritten).
- Route access matrix and automated regression test: `scripts/check-workspace-routes.mjs` (`npm run check:routes`).
- Note: client-side route guards are UX/access-control layers. Sensitive data must continue to be protected by Supabase RLS and server-side API authorization.
